# G-HAL Architecture Audit — 2026-10-23

Phase 1 audit per the Master Build Prompt, covering both candidate repositories
(`HeshamRefai/ghal`, this repo, and `HeshamRefai/g-hal`), followed by the
implementation decisions taken for the first vertical slice.

## 1. Repository selection

Two candidate codebases were audited:

| | `ghal` (this repo) | `g-hal` |
|---|---|---|
| Shape | Modular monolith: pnpm workspaces, Hono REST API, Supabase/Postgres migrations, 5 core modules, unit tests | Single Vite/React/tRPC app (claimed) |
| Reality check | Modules exist and are substantive: `process-ir` (validated IR), `runtime` (governed execution), `governance` (deny-by-default policy engine), `protocols` (P2/P4/P5/P7 state machines), `audit` (SHA-256 chain) | README promises 33 routes / 28 dashboards; the clone contains **19 files**. `App.tsx` imports ~30 page components that do not exist; the build script references `api/boot.ts` which does not exist; no `vite.config`, no `index.html`, no `tsconfig` — **cannot build** |
| Database | Postgres migrations with RLS on 18 tables + append-only audit | Drizzle/MySQL schema only |
| Verdict | **Selected as base.** Real, testable core aligned with Modules F/G of the build prompt | Rebuilding it would be a from-scratch rewrite wearing an existing README |

Decision: build the vertical slice on `ghal`. Per the build prompt, the existing
implementation of `g-hal` demonstrably prevents progress (it cannot compile),
while `ghal`'s IR/runtime/governance/audit modules are directly reusable.

## 2. Findings on this repo (pre-change)

### Real defects fixed in this branch
1. **Broken workspace setup.** `package.json` declares `packageManager: pnpm@9`
   and a `workspaces` field, but pnpm ignores that field — it requires
   `pnpm-workspace.yaml`, which was missing. Documented `pnpm install` therefore
   never installed workspace dependencies (hono, zod, tsx). Added `pnpm-workspace.yaml`.
2. **Broken vitest aliases.** `@ghal/process-ir` and `@ghal/runtime` aliased to
   `src/` directories that contain `types.ts` / `engine.ts` and no `index.ts` —
   2 of 4 pre-existing test files could not even be collected. Aliases now point
   at exact files (mirrored in `tsconfig.base.json` paths).
3. **Cross-tenant data exposure in the API.** The API uses the Supabase
   *service-role* key, which bypasses RLS, yet `GET /processes`,
   `GET /processes/:id/versions`, `GET /cases/:id`, `GET /exceptions`, and
   `GET /audit-events` had **no `tenant_id` filter** — any caller with any valid
   tenant header could read every tenant's data. Fixed by adding explicit tenant
   filters (RLS bypass means filters are the only isolation at this layer).
4. **Missing entry-point guard.** `index.ts` called `serve()` at import time,
   making the app unimportable for tests. Now guarded; app is exported.

### Known issues NOT fixed in this branch (documented, not hidden)
- The tenant middleware calls `supabase.rpc('set_config', ...)` intending to set
  `app.tenant` for RLS. This does not work as written (the setting does not
  propagate to subsequent requests on other connections, and is moot under the
  service-role key anyway). Left as-is; the correct fix is either scoped
  postgrest clients per request or dropping service-role for user JWTs.
- `.env.example` contains a **real anon key** for a live Supabase project
  (`glzrohbiswtokurwuwxx`). Anon keys are public-by-design and safe *if* RLS
  policies are correct, but the README says "keys are present", which invites
  committing the service-role key next. Recommend rotating and scrubbing.
- `apps/web` is a layout shell with no pages — there is no UI.
- `domain/` and `modules/model-gateway/` are referenced in workspaces/tsconfig
  but do not exist.
- `apps/web` is Next.js 14 while nothing consumes it; the API is the only
  functioning surface.

## 3. What was implemented (Phase 2 + 3 — the vertical slice)

First market per the build prompt: **digital marketing agencies**; use case:
**campaign brief → launched approved campaign**.

New zero-dependency modules (deterministic; no LLM anywhere in the loop):

| Module | Build-prompt mapping | Contents |
|---|---|---|
| `@ghal/ingestion` | Module C | RFC-4180-ish CSV parser, task-event import, field/timestamp/dependency/duplicate validation, data-quality issues, analysis-capability report |
| `@ghal/metrics` | Module C/E | Baseline: cycle time, waiting, approval waiting, rework, cost; per-case/per-step/per-owner breakdowns. Raw timestamps = `measured`, aggregates = `calculated`. Nothing is labeled an estimate. |
| `@ghal/diagnostics` | Module C | Evidence-linked findings: approval bottleneck, waiting bottleneck, rework loop, unbalanced workload, unclear ownership. Each finding carries affected cases, values, the calculation, sample-bounded confidence (< 1), and limitations. Correlation ≠ causation is stated in every relevant finding. |
| `@ghal/redesign` | Module D | Deterministic proposal templates per finding type (conservative + substantial redesign where warranted). Proposals include changes, rationale, evidence refs, expected benefits (always `kind: 'estimate'` with assumptions), trade-offs, risks, testable success criterion, rollback conditions. `compileProposal` → new validated IR version (approval steps can never become `ALLOW`). `irFromObservedSteps` compiles the current operating model from imported evidence. |
| `@ghal/outcomes` | Module E | Measured before/after comparison with direction, deltas, sample sizes, confounders, and an explicit non-causal summary. |

API (`apps/api`):
- `src/store/json-file-store.ts` — dev persistence (JSON file, atomic writes,
  per-tenant buckets), implements the `AuditStore` interface so the existing
  P10 hash-chained `AuditWriter` works without Supabase. Also holds users/roles
  and computes the 6 conceptual permissions (view/propose/approve/execute/configure/admin).
- `src/vertical-slice.ts` — the loop as HTTP endpoints (all tenant-scoped,
  permission-checked server-side, audited): create process → import CSV →
  baseline → diagnostics → proposals → approve/reject (creates **new version**,
  never rewrites history) → version history → **rollback as a new version** →
  open case pinned to a version → record execution events (step ids validated
  against the pinned IR) → import outcomes → compare with baseline → audit trail.
- `src/dev-server.ts` — boots the slice without Supabase (`GHAL_DATA_DIR`,
  seeded pilot tenant + admin/manager/operator users).

## 4. Verification (Phase 4)

- `pnpm test` — **73/73 passing** (9 files), including:
  - golden-fixture metric tests with independently computed expected values;
  - diagnostic accuracy tests on engineered fixtures (known approval bottleneck,
    rework loop, workload imbalance) and a healthy-process negative test;
  - proposal schema + IR compilation + history-preservation tests;
  - a 14-assertion integration test driving the whole loop over HTTP:
    import → baseline → diagnose → propose → operator **denied** approval →
    manager approves → v2 active → case events → outcomes → comparison →
    rollback → SHA-256 audit chain verified end-to-end;
  - tenant-isolation test (second tenant sees nothing, gets 404).
- `pnpm typecheck` (`tsc -p tsconfig.json`) — clean.
- Dev server smoke-tested live: boots, authenticates, serves the loop.

## 5. Deliberately NOT done (honest scope)

- **No UI.** The six Command Center screens are not built; `apps/web` remains a
  shell. The loop is fully exercised through the API.
- **No LLM in the loop.** Proposal generation is deterministic templates. An LLM
  synthesis layer belongs behind the same schemas (`validateProposal`,
  `validateIR`) when added.
- **No real external integrations.** No ad-platform/email actions exist; nothing
  claims to have launched anything.
- **Supabase path for the new endpoints is not implemented** — the `JsonFileStore`
  is the seam; the migrations already define the target tables.
- Pre-existing gaps listed in §2 remain as documented.
